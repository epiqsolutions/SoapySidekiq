# Portable ThreadSanitizer validation, 2026-10-21

Source: master `b081d8bc8a9162d57d28bf3ef2a61f69600cfd08` through #138,
plus this PR's workflow/documentation changes. No C++ source changes.

All 484 individual portable cases pass in a fresh Clang 18.1.8 TSan build on
the existing Linux x86 node (Ubuntu 22.04 userland, Linux 6.5 kernel). All 33
CTest entries complete successfully. There are no ThreadSanitizer reports,
compiler warnings, race suppressions, or altered synchronization paths.

## Setup and reproduction

The default randomized address layout previously prevented startup. Disabling
ASLR for this process with `setarch -R` lets the runtime start; no host sysctl
was changed. GCC 11's runtime then reported double mutex locks and lacked the
`pthread_cond_clockwait` interceptor. Clang 14's runtime handles that call but
lacks `pthread_mutex_clocklock`, used by `std::timed_mutex` in TX status polls.
Its report resolves to that mutex's unlock after the unobserved timed lock.
The [GCC discussion](https://gcc.gnu.org/pipermail/gcc-patches/2021-May/570244.html)
and [LLVM 18 implementation](https://github.com/llvm/llvm-project/blob/llvmorg-18.1.8/compiler-rt/lib/tsan/rtl/tsan_interceptors_posix.cpp)
record the missing-interceptor issue and the newer interceptor respectively.
Those older runs are not passes. No driver locking was changed to accommodate
them, and no sanitizer checks were disabled.

Official LLVM 18.1.8 Ubuntu packages were downloaded from
[apt.llvm.org](https://apt.llvm.org/) using its signed package index, then
extracted into ignored `build/llvm18-toolchain/root`. The compiler and sanitizer
runtime come from the same release. Existing system compiler packages and host
settings were not changed. The local loader path selects the extracted LLVM
shared libraries; ordinary installed Clang 18 needs no such extraction setup.

With Clang 18 available, run from the repository root:

```sh
cmake --preset non-hardware-tsan -DCMAKE_CXX_COMPILER=clang++-18 \
  -DPython3_EXECUTABLE=/usr/bin/python3
cmake --build --preset non-hardware-tsan --parallel 2
setarch "$(uname -m)" -R env TSAN_OPTIONS=halt_on_error=1 \
  tests/non_hardware/run_suite.sh build/non-hardware-tsan
```

The local fresh build used `build/tsan-clang18-validation` with the equivalent
root CMake options and the extracted compiler's absolute path. Node-local logs
are `build/tsan-clang18-validation.log` and that build directory's `suite.log`.
Earlier failed-runtime/interceptor runs remain in `build/tsan-native-validation.log`
and `build/tsan-clang-validation.log`. These ignored paths are not remotely
attached evidence. CI adds a Clang 18 / Ubuntu 24.04 job with the same process
setup, counted suite, failure propagation, and uploaded logs. Its results must
be checked separately from this local run.

## Limits

This validates instrumented portable components and production-method fixtures.
It does not instrument the full concrete driver, proprietary SDK, device DMA,
or physical callbacks/PPS. The ordinary SDK builds and optional concrete-driver
integration remain separate checks. Repeat affected tests on later changes and
the final candidate; the earlier hardware campaign is unchanged.
